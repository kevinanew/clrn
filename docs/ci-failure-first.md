# Web CI 失败优先调度

画面工作流保留 3 套件 × 3 语言的 9 个分片，动画工作流保留 7 个分片。
两个工作流分别安排自己的历史失败项；部署入口调用时，历史来源是同一个
Release 验证工作流，并用套件各自的计划附件区分。端到端、功能、交互工作流
各只有一个重型任务，继续完整执行。静态门禁继续独立执行。

每轮流程：

1. 从当前提交生成完整分片和账号分配，固定并核验 Release 记录。
2. 查询同 workflow ID、事件、分支、来源仓库的最近较早运行。
   再校验计划附件中的仓库、PR 编号、ref、workflow、配置指纹和完整分片清单。
   计划的 `sha` 记录实际测试提交（PR 中为 merge SHA），`head_sha` 记录来源分支提交
   （PR 中取事件的 `pull_request.head.sha`），并与历史运行 API 的 `head_sha` 核对归属。
   缺少 `head_sha` 的旧计划不能可靠校验来源，回退当前全量。
3. 如历史有效，仅将未成功的分片放入 `priority`。没有历史或任何证据不可靠时，
   将当前完整计划放入 `remaining`，直接执行全量。
4. `remaining` 通过 `needs: [accounts, priority]` 和明确条件，等待优先阶段成功。
   优先阶段失败或取消时，不创建剩余重型分片。
5. 保留原检查名称的 `visual` / `animations` 矩阵门禁使用 `always()`，
   核对两个阶段结论及互斥完整分区。非空阶段必须成功；空阶段必须被跳过。
   优先通过、剩余未执行不能使完整门禁通过。

两阶段使用同一份测试实现，原账号 concurrency、手机/桌面覆盖、视觉阈值、
业务断言、重试次数、诊断与报告步骤保持不变。已通过的优先分片不在剩余矩阵内，
不会重复执行。Release 的完整应用提交、标签、大小及 SHA-256 在规划时固定，
每个 runner 仍独立下载并验证该附件。各分片所需的局部准备与原工作流保持一致。

## 连续修复与异常回退

`ci-plan-visual-<attempt>` / `ci-plan-animations-<attempt>` 附件在测试前保存完整
计划，保留 30 天。即使剩余分片没有创建，下一轮仍从当前配置构造完整覆盖；
上轮被失败优先阶段阻止的分片继续留在剩余计划。

历史 API 使用 `filter=all` 分页读取各 attempt，再按稳定分片标识选择最新
`run_attempt`，保留同一提交未重跑的已成功分片，兼容原生 Re-run failed jobs。
取消、跳过、超时或未知结论都不是成功；被失败阶段阻止的
剩余任务不会被误认为通过。任务缺失且无法解释、重复标识、未知标识、附件过期、
权限/API 故障、最近运行尚未结束、配置不兼容、新增/删除/重命名分片均回退全量。
不会越过不可靠的最近历史使用更旧失败状态。旧提交成功只影响顺序，不免除当前验证。

工作流需要 `actions: read` 读取历史；部署调用入口也声明该只读权限。
查询失败（包括 fork 权限不足）只影响顺序。构建记录核验失败属于真实准备失败，
会阻止测试和完整门禁。

## 手动全量与运行摘要

在画面或动画工作流的 **Run workflow** 中启用 `full_run`，可忽略历史，
执行当前 `suite`、模式等参数选择的完整计划。要完整回归，请选择 `suite=all`，
画面使用 `mode=compare` 且清空 `filter`，动画关闭 `update_snapshots`。
无历史、历史全部通过时，也重新执行当前提交的完整计划。

规划摘要列出历史来源、当前测试提交、来源分支提交、优先/剩余分片及固定应用构建；门禁摘要列出
规划与两个阶段的结论。失败分片的原报告继续由实际执行任务上传。

## 验证

本地：`npm run check`，其中调度单测覆盖连续三轮失败、7/9 分片、来源隔离、
计划变化、取消/跳过、API 分页、附件读取和完整门禁的拒绝条件。

真实 PR 验收尚需在 GitHub Actions 执行，不能用本地单测代替：

1. 建立包含该实现的 PR，首轮确认 9/7 分片均启动，记录 run URL 与失败分片。
2. 提交业务修复，保持调度和分片配置不变。检查新 run 的完整计划附件和 Jobs API：
   优先阶段只启动历史失败项，剩余分片首个 `started_at` 晚于所有优先分片的
   `completed_at`。优先仍失败时，剩余重型分片数量应为 0，原名门禁应失败。
3. 再提交修复并通过优先阶段，确认本轮所有分片各执行一次，原名门禁最终成功。
   同时核对仓库实际 required checks，无需调整保护规则。
4. 分别演练取消、手动 `full_run` 和配置变更，确认取消不放行、后两者执行全量。
5. 分开记录优先阶段重型任务启动数、排队时间、提交至首个失败反馈时间，以及
   完整成功总耗时；不可把阶段化后更快的失败反馈当成全量成功加速。

可用 `gh api --paginate 'repos/kevinanew/clrn/actions/runs/<run-id>/jobs?filter=all'`
采集任务的 `created_at`、`started_at`、`completed_at`、结论与名称。
真实 PR 的运行链接和实测时间应在完成上述验收后补充，本文不预填未测量数据。
